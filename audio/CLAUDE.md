# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Spring Boot 4.1 / Java 21 backend (`com.nostalgiaana.audio`) for an audio/video platform ("Nostalgiaana") serving Hindi film songs, trivia, interviews, and podcasts. Maven build via the wrapper. Auth, users, categories, content (now split into Shows and Audios), payments, and admin are fully wired (controller → service → repository → entity); the only schema table with no JPA counterpart at all is `notifications`. The product was pivoted to a leaner MVP partway through (see migration `V4` below): playlists, favorites, listening history, and subscriptions were designed in `V1` and then deliberately dropped — they are not "not built yet", they were built and removed, so don't resurrect them without checking with the user first. This backend is paired with a Flutter frontend in the sibling `frontend/` directory of this monorepo — see the root `CLAUDE.md`.

## Commands

Use the Maven wrapper, not a system `mvn` (note: the wrapper's auto-download has been flaky in this environment due to a Windows file-lock issue extracting the distribution into `%TEMP%`; if `./mvnw.cmd` fails with a `Rename-Item`/access-denied error, fall back to a system `mvn` of the same version — 3.9.16 — if one is installed).

```
./mvnw.cmd spring-boot:run         # run the app (PowerShell/cmd)
./mvnw spring-boot:run             # run the app (bash)

./mvnw.cmd test                    # run all tests
./mvnw.cmd test -Dtest=AudioApplicationTests   # run a single test class
./mvnw.cmd test -Dtest=ClassName#methodName    # run a single test method

./mvnw.cmd clean package           # build the jar (target/*.jar)
./mvnw.cmd clean package -DskipTests
```

### Required services

No test profile exists (no Testcontainers/H2) — the single existing test (`AudioApplicationTests`) is a full `@SpringBootTest` that loads the real context. **Production and typical local dev now point at the same cloud services** — Supabase Postgres, Upstash Redis, Cloudflare R2 — via env vars (`DB_NAME`/`DB_USER`/`DB_PASS`, `REDIS_HOST`/`REDIS_PORT`/`REDIS_PASSWORD`/`REDIS_SSL`, `STORAGE_ENDPOINT`/`STORAGE_KEY`/`STORAGE_SECRET`/`STORAGE_BUCKET`); every one of them still has a `localhost`-pointed default in `application.yaml` for genuinely-local Postgres/Redis/MinIO containers if you'd rather not touch the cloud services. See root `CLAUDE.md` for the full list of critical, non-obvious config gotchas (PgBouncer/Hikari, Flyway baseline, R2 presigned-URL host) before assuming a fresh setup will "just work."

- MinIO/R2 bucket names: four buckets auto-created on startup by `StorageService.initBuckets` (wired via `MinioConfig`'s `MinioClient` bean): `audio-content`, `cover-images`, `video-content` (Shows), `profile-pictures` locally — but in production these four properties all collapse onto the single `STORAGE_BUCKET` value (one real R2 bucket, `nostalgiaana-media`, objects distinguished by key alone).
- Razorpay key/secret/webhook-secret default to placeholder strings — real payment-order creation and webhook signature verification will fail against the live Razorpay API until real test/live keys are set (env vars are not wired for these in `application.yaml`; edit the `razorpay:` block directly or override via `-D`/env if you add `${...}` placeholders).
- `admin.bootstrap.enabled` defaults to **`true`** (`ADMIN_BOOTSTRAP_ENABLED` env var overrides) — `AdminBootstrapRunner` upserts the phone in `admin.bootstrap.phone` (`9987092587`) to `role=ADMIN` on every single startup, resetting its password to `admin.bootstrap.password` each time. This guarantees the admin account always exists, but also means it's clobbered on every restart while enabled — don't rely on a manually-changed password for that account persisting across restarts. Check the real current value in the (gitignored) `.env` file or Render's dashboard, not this doc.
- `spring.servlet.multipart.max-file-size`/`max-request-size` are explicitly set to `2GB` (Spring Boot's undeclared defaults are 1MB/10MB, which silently broke any real audio/video upload before this was added) and `server.tomcat.max-swallow-size` is also raised to `2GB` to match — without that second property, a rejected oversized upload can manifest as a connection reset instead of a clean error.

## Architecture

**Package-by-feature.** Each top-level package under `com.nostalgiaana.audio` (`auth`, `user`, `category`, `content`, `storage`, `payment`, `admin`, `config`, `exception`) is a vertical slice with its own `Controller` → `Service` → `Repository` → JPA `Entity`, plus a `dto` sub-package for request/response shapes where needed. Follow this layering for any new feature rather than introducing a generic layered (controllers/, services/, repositories/) structure.

Entities use Lombok (`@Data @Builder @NoArgsConstructor @AllArgsConstructor`) and UUID primary keys (`GenerationType.UUID`). Repositories are plain `JpaRepository<Entity, UUID>` interfaces; query methods are derived (`findByX`) or `@Query` for anything more complex (e.g. `ContentRepository.searchContent`, `incrementPlayCount` — both currently unused dead code, left over from before the Shows/Audios split).

**Auth** (`auth/`): **phone-only, no email anywhere** — the `users.email` column and its check constraint were dropped in `V6`/`V7` (see Database migrations below); `User` has no `email` field, `SignupRequest`/`LoginRequest` have no email field. Signup (`POST /api/auth/signup`) is **multipart**, not plain JSON — a `data` part (JSON-encoded `SignupRequest`: firstName/lastName/phone/country/city/password) plus an optional `profilePicture` file part, validated to be `image/*` if present and uploaded to the `profile-pictures` bucket keyed by the new user's UUID. Signup creates the user and returns tokens immediately, no OTP step — **but note this happens regardless of admin-approval status** (see below), so a freshly-signed-up user gets a working JWT before any admin has approved them. Login is a two-step OTP flow, not a direct password check: `POST /api/auth/login` verifies the password, checks `isActive` then `approved` (in that order — see admin-approval gate below), generates a 6-digit OTP, stores it in Redis (`otp:<identifier>`, 5 min TTL), and **only logs it** (`AuthService`'s log line, no actual SMS/WhatsApp/email send exists anywhere in the codebase today — retrieve it directly from Redis for real testing: `GET otp:<identifier>`); `POST /api/auth/verify-otp` checks the OTP against Redis, capping attempts at 5 per TTL window (`otp:attempts:<identifier>`) before issuing the real access/refresh JWTs. Don't treat `/login` as the place where JWTs are minted — that only happens in `verifyOtp` and `signup`. `membershipStatus`/`membershipTier` values returned to clients are `"PREMIUM"` or `"STANDARD"`.

**Admin-approval gate** (`V8` migration, `users.approved`): every user row has an `approved BOOLEAN NOT NULL` column, `DEFAULT false` for anyone created after `V8` (pre-existing rows were backfilled to `true` so nobody already registered got locked out). New signups are therefore unapproved until an admin acts — but see above, signup itself still hands back a working JWT immediately; the gate only bites on the **next** `POST /api/auth/login` (`AuthService.login` throws `UserNotApprovedException` → `GlobalExceptionHandler` → `403` with body `{"error": "You have not been approved yet", ...}`, checked *after* the `isActive`/suspension check but *before* OTP generation). `AdminService.approveUser`/`PATCH /api/admin/users/{id}/approve` flips it; `AdminUserResponse.approved` surfaces the flag to the admin user-management UI. The frontend (`sampleui/screens/login_screen.dart`) matches this 403 by comparing the exact error string `"You have not been approved yet"` — if that message text ever changes on the backend, update the frontend's `_pendingApprovalMessage` constant in the same commit or the "pending approval" dialog silently stops firing and falls back to a generic error.

**Security** (`config/SecurityConfig.java`, `auth/JwtAuthFilter.java`): stateless JWT, no sessions. `JwtAuthFilter` runs before `UsernamePasswordAuthenticationFilter`, validates the bearer token via `JwtService`, loads the `User`, and sets a `UsernamePasswordAuthenticationToken` with a single `ROLE_<UserRole>` authority (only if the user is still `isActive`). `UserRole` is `LISTENER | PREMIUM | ADMIN`; endpoint authorization is done with method-level `@PreAuthorize("hasRole('ADMIN')")` rather than path rules in `SecurityConfig`, which only declares `/api/auth/**`, `/api/categories` (exact match, not `/api/categories/**` — `GET /api/categories/{id}` still requires authentication), `/api/payments/webhook`, and `/actuator/**` as public — everything else requires authentication. CSRF, HTTP Basic, and form login are all disabled — this is a pure REST/JWT API. The webhook route is public because Razorpay calls it directly and authenticity is instead verified via HMAC signature (`Utils.verifyWebhookSignature`), not a JWT. CORS **is** configured (`SecurityConfig.corsConfigurationSource()`, driven by `cors.allowed-origins`/`CORS_ALLOWED_ORIGINS`, defaulting to `*`) — irrelevant for native Android/iOS/Windows clients, but already wired for a future browser-based (Flutter web) client without needing new setup.

**Error handling** (`exception/GlobalExceptionHandler.java`): business-rule failures throughout the service layer are thrown as plain `RuntimeException` with a user-facing message (e.g. `AuthService`, `CategoryService`, `ContentService`) and are globally caught and turned into a `400` with `{error, status, timestamp}`. `MethodArgumentNotValidException` (bean validation) is handled separately to surface the first field error. A catch-all `Exception` handler returns a generic `500` — note this also swallows framework-level routing exceptions like `NoResourceFoundException`, so hitting a genuinely unmapped/removed route returns `500` here instead of a clean `404`; that's existing behavior, not a regression, if you trip over it. When adding new business validation, throw `RuntimeException` with a clear message rather than inventing new exception types, to stay consistent with this pattern.

**Storage** (`storage/StorageService.java`, `config/MinioConfig.java`): wraps two `MinioClient` beans (`minioClient` for internal put/get/delete/bucket-management calls, `presignMinioClient` used only to compute presigned GET URLs — presigning is a pure local HMAC computation, no network call) built in `MinioConfig` from the `minio.*` properties. In production both `minio.endpoint` and `minio.public-endpoint` point at the same `STORAGE_ENDPOINT` (Cloudflare R2's real S3 API host) — unlike a self-hosted MinIO behind a reverse proxy, R2's S3 API endpoint is already externally reachable, so there's no need for two different hosts. **Do not point `minio.public-endpoint` at R2's separate "public dev URL" feature** — that host is already scoped to one bucket via its subdomain, so MinIO's path-style presigned URLs (which embed the bucket name in the path) 404 against it; this was a real, reproduced bug, fixed in the parent repo's commit `d3ec61c`. Locally, both still default to `http://localhost:9000` for a real local MinIO container. Presigned GET URLs are valid for 1 hour. `Content.hlsManifestPath` exists on the entity but nothing in the codebase ever writes it — media is served by presigning the raw upload, not an HLS manifest, for both audio and video.

**Content** (`content/`): `Content` has a `contentType` (`ContentType.SHOW | AUDIO`, `@Enumerated(EnumType.STRING)`, defaults to `AUDIO`) discriminating two parallel media kinds: Shows are **video** files (`rawVideoPath`, `video-content` bucket — e.g. Zoom recordings), Audios are audio files (`rawAudioPath`, `audio-content` bucket — e.g. songs). `ContentService.upload(ContentType, ...)` is one type-aware method (not two duplicated ones) that validates the uploaded media's declared MIME type matches (`video/*` for Shows, `audio/*` for Audios) and branches on which bucket/entity field to use; the optional cover/thumbnail is validated as `image/*` the same way. `getStreamUrl` branches the same way to presign from the correct bucket, and separately checks `content.isPremium && requester.role == LISTENER` to reject premium content for non-premium listeners (ADMIN and PREMIUM roles always pass this check). A private `findByIdAndType` guard backs `delete`/`updateMetadata` so that, e.g., deleting a known Audio's id through the Shows path fails as `"Content not found"` rather than silently operating on the wrong row — same message whether the id doesn't exist or just isn't that type, so cross-type probing doesn't leak which is true. `ContentController` only exposes read-only, any-authenticated-role browsing: `GET /api/content/shows`, `GET /api/content/audios`, `GET /api/content/{id}/stream`. **There is no longer a generic `POST /api/content`** — that overlapped with `AdminController` and was removed; all content creation goes through the admin endpoints below.

**Admin** (`admin/`): `AdminController` is class-level `@PreAuthorize("hasRole('ADMIN')")` and is split into two fully parallel resource groups — `/api/admin/shows` (multipart `data` + `video` + optional `thumbnail`) and `/api/admin/audios` (multipart `data` + `audio` + optional `thumbnail`) — each with create/list/update/delete. Plus `/api/admin/users` (list, excludes `ADMIN`-role accounts — this endpoint is specifically for classifying regular users into `PREMIUM`/`STANDARD`, not for managing other admins), `/api/admin/users/{id}` (`DELETE` = soft-ban, sets `isActive=false`, does not delete the row), and `/api/admin/users/{id}/approve` (`PATCH`, sets `approved=true` — see the admin-approval gate above). There is no admin-side "get stream URL by id" endpoint — reuse `ContentController`'s `/api/content/{id}/stream` (any authenticated role, including ADMIN, can call it) rather than adding a duplicate. `AdminBootstrapRunner` — see the bootstrap note under Required local services above.

**Payments** (`payment/`, `config/RazorpayConfig.java`): `RazorpayClient` is a `@Bean` built from `razorpay.key-id`/`razorpay.key-secret`. `PaymentService.createOrder` creates a Razorpay order and a local `Payment` row with `status="PENDING"`. The webhook handler verifies the signature, and on an `order.paid` event marks the `Payment` `SUCCESS` and sets the paying `User`'s role directly to `PREMIUM` — there is no subscription/expiry tracking at all (the `subscriptions` table and `payments.subscription_id` were dropped in `V4`), so `PREMIUM` is currently a permanent flag once any payment succeeds, not a time-boxed plan.

**Database migrations** (`src/main/resources/db/migration/`): Flyway, `validate`-only Hibernate DDL (`spring.jpa.hibernate.ddl-auto: validate`) — schema changes must go through a new `V<n>__description.sql` migration, never through entity/annotation changes alone. `V1` created the full original schema (users, categories, content + full-text search trigger/index, playlists, playlist_content, favorites, listening_history, subscriptions, payments, notifications) using Postgres enums; `V2` converts those enums to `VARCHAR` and drops the enum types; `V3` seeds the default categories; `V4` pivots to the MVP shape — drops `playlist_content`, `favorites`, `listening_history`, `subscriptions`, and `payments.subscription_id`; renames `users.name` to `first_name`/`last_name` and adds `country`/`city`; adds a check constraint requiring `email IS NOT NULL OR phone IS NOT NULL`; `V5` adds the Shows/Audios split — `content.content_type` (`VARCHAR(20)`, backfilled to `'AUDIO'`, `NOT NULL`, `CHECK (content_type IN ('SHOW', 'AUDIO'))`) and `content.raw_video_path`; **`V6` drops `users.email` entirely** (backfills a phone onto the one remaining email-only account first, then drops the now-obsolete email-or-phone check constraint) — phone becomes the sole identifier from here on; `V7` normalizes the bootstrap admin's phone to the bare 10-digit form (`admin.bootstrap.phone` in `application.yaml`) and backfills its `country`/`city`; `V8` adds `users.approved` (backfills existing rows to `true`, then sets `NOT NULL DEFAULT false` so only pre-`V8` users are grandfathered in — see the admin-approval gate above). When extending the schema, match this style (plain incremental `ALTER`/`DROP`/`CREATE` statements, no down-migrations, VARCHAR over Postgres enum types). Note also: against a *fresh* Supabase project, `spring.flyway.baseline-version: 0` must stay set (see root `CLAUDE.md`) or Flyway will mis-baseline and skip `V1`.

**Unimplemented / dormant surface area**: the `notifications` table from `V1` still exists in the schema with no entity, repository, service, or controller anywhere in `src/`. `firebase-admin` and `google-api-client` are present in `pom.xml` but unused anywhere in `src/` (only `User.googleId` exists as a placeholder column/field) — presumably for planned push notifications and Google login, not yet started. `User.profilePicPath` is written on signup but never read back out through any response DTO — there's no presigned profile-picture URL endpoint yet, it's write-only from the API's perspective today.
